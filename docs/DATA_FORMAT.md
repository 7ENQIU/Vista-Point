# Формат данных кампании

## Текущая версия

Версия схемы: `22`.

Схема `22` окончательно удаляет legacy-поле `visibility` из фактов, заготовок хотбара, результатов логики и сохранённых payload журнала. Миграция рекурсивно отбрасывает это поле; состав сущностей, идентификаторы фактов и остальные свойства не меняются. Будущие пользовательские проекции должны опираться на Knowledge State, а не на переключатель отдельного факта.

Схема `21` добавляет переносимую коллекцию `savedGraphViews`. Каждый сохранённый вид хранит стабильный ID, уникальное название, поисковый запрос и набор фильтров встроенных и пользовательских типов. Применение вида меняет только текущую проекцию графа и не создаёт событие; создание, переименование и удаление определения фиксируются событиями `graph.view.created`, `graph.view.renamed` и `graph.view.removed`.

Ручные координаты карточек намеренно не входят в сохранённый вид: они остаются локальной настройкой конкретного устройства. При удалении пользовательского типа его ID удаляется из сохранённых фильтров той же доменной операцией, поэтому кампания не получает битых ссылок.

Схема `20` добавляет переносимую коллекцию `customEntityTypes`. Пользовательский тип хранит стабильный ID, русскоязычное название и неизменяемый `baseType`. Базовый тип сохраняет специальную семантику существующих сценариев: пользовательский «Город» остаётся локацией для вложенности, а «Злодей» на основе NPC получает ролевые теги. Сущность и шаблон ссылаются на определение через необязательный `customTypeId`, не копируя название.

Пользовательский тип можно переименовать без изменения сущностей и шаблонов. Удаление разрешено только когда на него больше никто не ссылается. Создание, переименование и удаление фиксируются событиями `entity.type.created`, `entity.type.renamed` и `entity.type.removed`.

Схема `19` добавляет переносимую коллекцию `entityTemplates`. Шаблон хранит тип сущности и переиспользуемые поля полной карточки: краткое и полное описание, заметки ДМа, обычные и ролевые теги, а также значения пользовательских полей. Имя сущности, изображение, факты, состояние и история в шаблон не входят. Новая сущность всегда получает собственный ID и остаётся единственным источником данных для графа и библиотеки.

Название шаблона уникально внутри кампании без учёта регистра. Шаблон применяется только к сущности совпадающего типа; ссылки из пользовательских полей проверяются так же, как в обычной карточке. Создание и удаление шаблона фиксируются событиями `entity.template.created` и `entity.template.removed`. Удаление не меняет ранее созданные сущности.

Схема `18` добавляет переносимую коллекцию `customFieldDefinitions`. Определение хранит стабильный ID, русскоязычное название и тип `text`, `number`, `boolean` либо `entity_reference`; значения по-прежнему находятся только в `CampaignEntity.customFields` по ID определения. Миграция `17 → 18` выводит определения из прежних значений и сохраняет их без создания копий.

Название определения можно менять без перепривязки значений и правил. Тип существующего определения неизменяем: его смена могла бы сделать сохранённые значения несовместимыми. Определение можно удалить только когда его ID отсутствует во всех `customFields`, шаблонах карточек, условиях `custom_field` и результатах `set_custom_field`. Это ограничение проверяется доменом независимо от интерфейса.

> Схема `22` сохраняет legacy-слои прежней концепции там, где они нужны для безопасного перехода. World Time, глубина знания, Runtime Layer и старый Trigger Engine больше не являются активными частями рабочего интерфейса. Полная карта решений приведена в [инвентаризации legacy-данных](LEGACY_DATA_MIGRATION.md).

Очистка видимой истории не меняет экспортируемый `Campaign.eventLog`. Интерфейс хранит в `localStorage` только идентификатор последнего скрытого события отдельно для каждого проекта. Новые события после курсора снова показываются; очищенную историю можно восстановить без изменения данных проекта.

Undo/Redo также не переписывает и не удаляет журнал. Отмена добавляет событие `history.undo`, повтор — `history.redo`; оба ссылаются на исходное событие через `payload.targetEventId` и сохраняют его тип в `payload.targetEventType`. Первый срез поддерживает только последовательные обратимые изменения карточек, фактов и пользовательских предикатов. Неподдерживаемое событие сбрасывает доступный стек, поэтому восстановление никогда не строится на предположениях о неизвестных последствиях.

`HistoryEntry` пока является типизированной вычисляемой проекцией `Campaign.eventLog`, а не второй коллекцией в файле. Она добавляет группе события актуальный статус `applied`, `undone` или `recorded` и ссылку на исходную запись операции истории. Экспорт не дублирует данные, а импортированная история получает те же статусы детерминированно. Ограничение интерфейса в 500 записей применяется после фильтрации только к отрисовке и не сокращает `eventLog`.

Условие логики `field: "custom_field"` хранит `entityId`, стабильный `customFieldId`, типосовместимый оператор и ожидаемое значение. Результат `type: "set_custom_field"` хранит те же ссылки и новое значение. Тип берётся только из `Campaign.customFieldDefinitions`: числа поддерживают сравнение порядка, текст — проверки содержания, логические и ссылочные значения — равенство; для любого типа доступны `exists` и `not_exists`. Применение фиксирует наличие прежнего значения отдельно, поэтому Undo корректно отличает пустое поле от значения `false`, `0` или пустой строки.

Условие логического правила с `field: "relationship"` может хранить стабильную ссылку `predicateId`. Для совместимости со схемой `13` поле необязательно: прежние правила продолжают использовать legacy-поле `relationshipType`, а новые правила канваса записывают `predicateId`. Валидатор проверяет существование предиката, а вычисление сопоставляет факт по его ссылке, поэтому переименование пользовательского предиката не требует изменения правила.

Экспорт представляет собой оболочку `CampaignFile`. Она отделяет версию переносимого файла от версии внутренней схемы кампании:

Корневой объект `Campaign` содержит метаданные, мировое время, единые коллекции сущностей, связей и событий. Все ссылки используют постоянные идентификаторы.

Схема `10` добавляет `Campaign.calendar`. Внутреннее `worldTime` по-прежнему хранится как ISO-дата и остаётся единой монотонной шкалой для расписания, журналов и триггеров. Календарь является обратимой проекцией этой шкалы, поэтому смена названий или длины месяцев не переписывает уже сохранённые отметки времени.

Пользовательский календарь (`kind: "custom"`) содержит от 1 до 48 месяцев с постоянной длиной от 1 до 999 дней, необязательные дни недели и обозначение эпохи. Поля `epochWorldTime`, `epochYear`, `epochMonthId`, `epochDay`, `epochHour`, `epochMinute` и `epochWeekdayIndex` связывают выбранную мастером игровую дату с внутренним временем. Миграция схемы `9 → 10` добавляет обычный календарь и не изменяет `worldTime`, даты событий или историю.

Схема `11` исторически добавила каждой сущности массив `characterTags` и необязательное поле `locationLevel`. В актуальной модели `locationLevel` является только legacy-полем совместимости: приложение не создаёт, не редактирует, не отображает и не использует его при проверке или раскладке. Вложенность локаций определяется исключительно цепочкой фактов `located_in` / `contains`. `characterTags` по-прежнему редактируются у NPC и не смешиваются с обычными организационными `tags`.

Схема `12` добавляет сущности строку `dmNotes` и необязательный объект `image`. Изображение встраивается как `dataUrl` и хранится только в исходной сущности; допустимы PNG, JPEG, WebP и GIF размером до 5 МБ. SVG отклоняется при выборе и импорте. Событие замены содержит только имя файла, MIME-тип и время изменения, поэтому не дублирует base64-данные и помечается необратимым. Миграция `11 → 12` не меняет идентификаторы, ролевые теги, уровни локаций и сохранённую очередь legacy-логики.

Схема `13` добавляет коллекцию `predicates` и обязательную ссылку `predicateId` каждому факту в прежней коллекции `relationships`. Встроенные предикаты имеют стабильные идентификаторы вида `builtin:located_in`, прямое и обратное названия. Пользовательский предикат является отдельной сущностью данных и может использоваться многими фактами. Его переименование не меняет факты и их идентификаторы: все представления получают актуальные подписи по `predicateId`. Архивирование разрешено только при отсутствии активных фактов с этим предикатом; встроенные предикаты защищены. Операции записывают события `predicate.updated` и `predicate.archived`. Миграция `12 → 13` сохраняет идентификаторы связей, сущностей и изображений, создаёт встроенный предикат для каждого прежнего типа и не дублирует факты.

Схема `14` удаляет рабочее различие сущностей на `draft` и `active`. Миграция переводит прежние черновики в обычные рабочие записи и отключает правила, которые читали или меняли жизненный статус.

Схема `15` исторически удалила поле `visibility` из сущности. Начиная со схемы `22`, то же legacy-поле удалено и из фактов и связанных с ними заготовок.

Схема `16` добавляет результат логического правила `create_fact`. Он хранит исходную и целевую сущности, стабильный `predicateId`, направленность и описание будущего факта. Миграция `15 → 16` меняет только номер схемы: сущности, факты и прежние правила не изменяются.

Иерархические плашки карточек не сохраняются в файле. Они вычисляются из ближайшей активной связи: вложенная локация → родительская локация, сцена → ближайшая локация, участник → сцена. Миграция `10 → 11` добавляет пустые ролевые теги, не меняя существующие сущности, связи, календарь или историю.

Каждая связь остаётся отдельным объектом даже при пакетном создании из интерфейса. Тип `participates_in` означает, что сущность-источник участвует в сцене, событии или другой сущности-цели. Пакетный выбор не меняет формат файла и не требует повышения версии схемы.

Удалённые из рабочих представлений сущности и связи сохраняются в своих коллекциях со статусом `archived`. События `entity.archived` и `relationship.archived` описывают действие и затронутые зависимости. Это совместимо с первой версией схемы, поскольку статус жизненного цикла уже является частью модели; физическое удаление из экспортируемого файла не выполняется.

Редактирование карточки не меняет структуру сущности и совместимо с первой версией схемы. Событие `entity.updated` хранит `changedFields`, а также объекты `before` и `after` только для действительно изменённых полей. Это позволяет проследить изменение и подготовить безопасный Undo без копирования сущности.

Начиная со схемы `2`, каждая сущность содержит коллекцию `state`. Пример параметра:

```json
{
  "id": "uuid",
  "name": "Здоровье",
  "category": "resource",
  "valueType": "integer",
  "value": 24,
  "updatedAt": "2026-08-20T12:00:00.000Z"
}
```

Допустимые категории: `life`, `social`, `story`, `information`, `spatial`, `resource`, `custom`. Допустимые типы первого среза: `boolean`, `integer`, `decimal`, `text`. Идентификаторы и названия параметров уникальны внутри сущности.

Схема `3` добавляет отдельную коллекцию `knowledge` на уровне кампании. Запись не изменяет World Truth в карточке сущности и описывает представление партии или конкретной сущности:

```json
{
  "id": "uuid",
  "campaignId": "uuid",
  "subjectType": "party",
  "content": "В старом маяке есть тайный вход",
  "status": "suspected",
  "confidence": 65,
  "truth": "unknown",
  "source": "Слух в порту",
  "relatedEntityIds": ["entity-uuid"],
  "createdAt": "2026-08-20T12:00:00.000Z",
  "updatedAt": "2026-08-20T12:00:00.000Z"
}
```

`subjectType` принимает `party` или `entity`; во втором случае обязателен `subjectEntityId`. Статусы знания: `unknown`, `suspected`, `known`, `confirmed`, `false`, `forgotten`. Поле `truth` (`unknown`, `true`, `false`) хранит отношение записи к World Truth, а не меняет объективные данные. `relatedEntityIds` связывает одну запись с существующими сущностями без их копирования.

Схема `4` добавляет `logicRules`. В старых файлах правила могли читать и менять технический жизненный статус сущности. Начиная со схемы `14` этот сценарий считается устаревшим: новые правила работают с параметрами состояния, фактами, знаниями и мировым временем.

```json
{
  "id": "rule-uuid",
  "campaignId": "uuid",
  "name": "NPC ранен",
  "description": "Предложить изменение статуса при низком здоровье",
  "enabled": true,
  "groupOperator": "all",
  "conditions": [{
    "id": "condition-uuid",
    "entityId": "entity-uuid",
    "field": "state",
    "stateId": "state-uuid",
    "operator": "less",
    "value": 10
  }],
  "effects": [{
    "id": "effect-uuid",
    "entityId": "entity-uuid",
    "type": "set_lifecycle_status",
    "value": "active"
  }],
  "executionMode": "require_confirmation",
  "createdAt": "2026-08-20T12:00:00.000Z",
  "updatedAt": "2026-08-20T12:00:00.000Z"
}
```

Поддерживаются группы `all`, `any`, `none`; операторы `equals`, `not_equals`, числовые сравнения, `contains`, `not_contains`, `exists`, `not_exists`; режимы `require_confirmation` и `suggest_only`. Предварительная проверка не записывается в Campaign и не меняет данные. Подтверждённое применение нескольких эффектов создаёт одно событие `logic.rule.applied` со снимком всех изменений. Эффект `create_fact` создаёт обычный `Relationship` в единой коллекции; повтор уже существующего факта не дублируется.

Схема `5` добавляет `sessions` и необязательный `activeSessionId`. Сессия ссылается на единственную текущую Scene, участников и посещённые сцены по идентификаторам, хранит реальное и мировое время начала/завершения и редактируемую сводку. Карточки участников и DM Screen являются проекциями исходных сущностей.

Схема `6` добавляет `scheduledEvents`. Запланированное мировое событие содержит дату наступления, статус `scheduled`, `completed` или `cancelled`, признак сюжетной значимости и ссылки на исходные сущности. Перевод времени создаёт `world.time.changed`, а наступившие записи — `world.scheduled_event.triggered`; изменение применяется только после подтверждения мастера. Быстрые проверки не создают отдельную коллекцию и хранят результат в событии `session.check.resolved` активной сессии.

Схема `7` добавляет каждой сущности объект `origin` и коллекцию `encounters`. Обычная сущность получает происхождение `preparation`; Quick Create использует `session_quick_create`, хранит идентификаторы исходных сессии и сцены, мировое время и признак `processed`. Очередь является фильтром единой коллекции `entities`, а не копией данных.

`Campaign.encounters` хранит экземпляры проведения подготовленных сущностей типа `encounter`. Экземпляр ссылается на сессию, сцену и участников по идентификаторам, содержит стороны, инициативу, временные эффекты, раунд, текущий ход и подтверждённый исход. HP не копируется в столкновение: он читается и изменяется как целочисленный параметр `HP` исходной сущности в State Layer.

Схема `8` заменяет плоские поля `groupOperator` и `conditions` правила на корневое дерево `conditionGroup`. Узел имеет `kind: "group"` или `kind: "condition"`; группа содержит дочерние узлы и оператор `all`, `any`, `none` либо `count`. Для `count` поле `minimum` задаёт минимальное число выполненных непосредственных дочерних узлов. Глубина ограничена пятью уровнями.

Условия схемы `8` проверяют состояние сущности, существование типизированной направленной связи, статус знания партии или конкретной сущности и мировое время. Старые условия жизненного статуса читаются только для совместимости. Все ссылки остаются идентификаторами исходных данных. Предпросмотр рекурсивно объясняет результат каждой группы и каждого условия, а последствия по-прежнему применяются атомарно только после подтверждения мастера.

Схема `9` добавляет правилу объект `trigger`: источник проверки (`manual`, `on_change`, `world_time`), задержку в минутах игрового времени и режим повторения (`once`, `rearm`). Коллекция `logicTriggerStates` хранит техническое состояние перехода условия из невыполненного в выполненное и не является отдельной игровой сущностью.

`logicActivations` хранит прослеживаемую историю срабатываний со статусами `pending`, `applied`, `dismissed` и `invalidated`, исходным событием, временем постановки и наступления, а также снимком объяснений условий и последствий. Перед применением ожидающего срабатывания актуальные условия проверяются повторно. Явно разрешённый режим `automatic` обрабатывается локально; автоматическая цепочка ограничена двадцатью применениями за один пересчёт.

У события кампании может присутствовать `sessionId`. Все значимые изменения, созданные во время активной встречи, получают этот идентификатор и входят в её Timeline. Одновременно допускается не более одной сессии со статусом `active`.

При импорте проверяются:

- сигнатура и версия формата файла;
- версия схемы кампании;
- обязательные поля и даты;
- принадлежность вложенных объектов кампании;
- допустимые типы сущностей и связей;
- уникальность идентификаторов сущностей, связей, знаний, правил, сессий и событий;
- отсутствие связей и событий, указывающих на отсутствующие сущности.
- целостность субъекта и связанных сущностей Knowledge State.
- целостность сущностей и параметров состояния, на которые ссылаются условия и последствия.
- целостность настроек триггеров, исходных событий и статусов очереди срабатываний.
- целостность текущей сцены, участников, истории посещений и ссылок событий на сессии.

## Совместимость и миграции

- `schemaVersion` обязателен для каждого сохранения и экспорта.
- Изменение структуры требует функции миграции и теста на реальных образцах предыдущей версии.
- Перед необратимой миграцией приложение должно создать резервную копию и объяснить последствия.
- Неизвестную более новую версию нельзя молча перезаписывать.
- Схема `1` автоматически преобразуется в схему `2` добавлением пустой коллекции `state` каждой сущности.
- Схемы `1` и `2` преобразуются в схему `3` добавлением пустой коллекции `knowledge` кампании.
- Схемы `1`–`3` преобразуются в схему `4` добавлением пустой коллекции `logicRules`.
- Схемы `1`–`4` преобразуются в схему `5` добавлением пустой коллекции `sessions`.
- Схемы `1`–`5` преобразуются в схему `6` добавлением пустой коллекции `scheduledEvents`.
- Схемы `1`–`6` преобразуются в схему `7` добавлением происхождения сущностей и пустой коллекции `encounters`.
- Схемы `1`–`13` преобразуются в схему `14`: сущности со статусом `draft` становятся обычными рабочими сущностями, а правила с условиями или последствиями прежнего жизненного статуса сохраняются, но отключаются.
- Схемы `1`–`14` преобразуются в схему `15`: legacy-поле удаляется из сущностей.
- Схемы `1`–`15` преобразуются в схему `16` без изменения уже сохранённых сущностей, фактов и правил.
- Схемы `1`–`16` преобразуются в схему `17` с десятью пустыми слотами хотбара.
- Схемы `1`–`17` преобразуются в схему `18`; прежние примитивные значения `customFields` получают определения с выведенным типом, а новые кампании начинают с пустой схемы полей.
- Схемы `1`–`18` преобразуются в схему `19` добавлением пустой коллекции шаблонов карточек; сущности, факты, правила и пользовательские поля не изменяются.
- Схемы `1`–`19` преобразуются в схему `20` добавлением пустой коллекции пользовательских типов; существующие сущности и шаблоны продолжают использовать встроенные типы.
- Схемы `1`–`20` преобразуются в схему `21` добавлением пустой коллекции сохранённых видов графа; поиск, фильтры, сущности и локальная раскладка не изменяются.
- Схемы `1`–`21` преобразуются в схему `22`: legacy-поле `visibility` удаляется из фактов, хотбара, логики и payload журнала.
- Схемы `1`–`7` преобразуются в схему `8`; плоские правила Logic Layer оборачиваются в корневую группу без изменения их смысла.
- Схемы `1`–`8` преобразуются в схему `9`; существующие правила получают ручной триггер, а состояние и очередь срабатываний создаются пустыми.
- Схемы `1`–`9` преобразуются в схему `10`; добавляется обычное календарное представление без изменения внутренних отметок времени.
- Схемы `1`–`10` преобразуются в схему `11`; локации получают числовой уровень, NPC — отдельные ролевые теги, а прежние данные сохраняются без изменения смысла.
- Схемы `1`–`11` преобразуются в схему `12`; сущности получают отдельные заметки ДМа и место для одного локального изображения.
- Схемы `1`–`12` преобразуются в схему `13`; прежние связи получают ссылки на стабильные встроенные предикаты без смены идентификаторов.
- Перед преобразованием локальной кампании исходные данные сохраняются в IndexedDB как страховочная копия `before-migration`.

Сейчас поддерживается полный экспорт, повторный импорт собственного файла и миграция схем `1`–`21` в актуальную схему `22`. Выборочный экспорт и отчёт о частичных конфликтах пока не реализованы.

## Локальные настройки представления

Расположение узлов Campaign Graph не является частью формата Campaign. Оно хранится отдельно в `localStorage` браузера, версионируется собственным форматом и разделяется по идентификатору кампании и режиму графа. Поэтому перемещение узлов не меняет игровые данные и не создаёт событий, а локальная раскладка не входит ни в JSON-экспорт, ни в `savedGraphViews` и не переносится на другое устройство.
