# Инвентаризация legacy-данных перед новой схемой

## Назначение

Текущая схема `13` вводит стабильные предикаты и факты, но всё ещё сохраняет поля прежней концепции Vista Point. Удалять legacy-коллекции одновременно с изменением интерфейса небезопасно: локальные проекты могут содержать знания наблюдателей, сессии, расписания и уже выполненные правила. Эти данные сохраняются в IndexedDB, резервных копиях и экспорте, но не участвуют в текущем рабочем сценарии.

## Политика переходного периода

- Новая навигация и карточки читают только сущности, связи, состояние и журнал.
- Коллекция `knowledge` не участвует в поиске и не редактируется.
- Старый Trigger Engine не вызывается после изменений проекта; правила и очереди не исполняются в фоне.
- World Time, календарь, расписание, встречи и столкновения не имеют активных элементов управления.
- Экспорт продолжает включать legacy-поля внутри схемы `13`; перед миграцией локально создаётся страховочная копия.
- Физическое удаление legacy-полей допускается только после резервной копии, повышения версии схемы и тестов импорта всех поддерживаемых версий.

## Карта данных

| Данные схемы 13 | Состояние сейчас | Назначение в новой модели |
| --- | --- | --- |
| `entities` | активно | `Entity`; идентификаторы сохраняются |
| `relationships` | активно | будущие `Fact / KnowledgeRelation`; тип станет ссылкой на `Predicate` |
| `eventLog` | активно | источник для будущих `HistoryEntry`; Undo/Redo проектируется отдельно |
| `state` сущности | активно переходно | кандидат на пользовательские поля и значения логики |
| `customFields` | активно | основа типизированных пользовательских полей после нормализации |
| `knowledge` | только сохранение | будущий необязательный модуль `KnowledgeState`; в ядро не переносится |
| `logicRules` | только сохранение | переносимые правила позже преобразуются в узлы `LogicView` |
| `logicTriggerStates` | только сохранение | не переносится; это состояние старого исполнителя |
| `logicActivations` | только сохранение | не переносится; остаётся частью legacy-истории |
| `worldTime`, `calendar` | только сохранение | не входит в новую рабочую модель |
| `scheduledEvents` | только сохранение | не входит в новую рабочую модель |
| `sessions`, `activeSessionId` | только сохранение | архив прежнего Session Mode; не активирует интерфейс |
| `encounters`, `activeEncounterId` | только сохранение | архив прежнего Runtime Layer |
| `origin.worldTime` | только совместимость | будет заменено обычной временной отметкой происхождения |
| `CampaignEvent.worldTime` | только совместимость | новое событие истории использует `createdAt` без World Time |

## Предлагаемая последовательность новой схемы

1. Добавлять новые структуры рядом с legacy-коллекциями схемы `13`, не изменяя их до полной миграции.
2. Скопировать сущности с прежними идентификаторами и проверить количество активных и архивных объектов.
3. Создать предикат для каждого используемого типа отношения и преобразовать связи в факты.
4. Сохранить исходные legacy-коллекции в явно версионированном архивном блоке либо в страховочной копии до подтверждения миграции.
5. Перенести только совместимые ручные правила; правила знаний и World Time отметить как непереносимые, не выполнять их.
6. Сформировать историю из событий, не используя её как стек Undo/Redo.
7. Проверить ссылки, экспорт, повторный импорт и идемпотентность миграции.
8. Только после этого прекратить обязательную запись полей World Time и удалить старые application/UI-модули.

## Обязательные проверки новой миграции

- количество сущностей и их идентификаторы совпадают до и после перехода;
- каждая активная связь имеет источник, цель и созданный предикат;
- архивные сущности и связи не становятся активными;
- старые знания, сессии, расписания и правила доступны в страховочной копии;
- ни одно старое автоматическое правило не выполняется при открытии или редактировании;
- повторная миграция не создаёт дубликаты;
- повреждённые ссылки останавливают импорт до записи;
- новая история очищается независимо от данных проекта.

## Решение о повышении версии

Версия `13` добавляет `Predicate` и связывает каждый существующий факт с предикатом через `predicateId`, сохраняя идентификаторы прежних записей `relationships`. Полное переименование коллекции и удаление legacy-полей отложены до отдельной проверяемой миграции; текущий переход остаётся обратимым через страховочную копию.
